# 在线问卷系统关键逻辑说明

[文档目录](../../README.md) · [仓库首页](../../../README.md) · [运行代码](../../../code/README.md) · [测试材料](../../../test/README.md)

本文结合数据库设计和当前后端代码，说明问卷版本、填写路径、提交一致性及统计口径的实现。

## 1. 问卷定义与收集控制分离

`surveys` 保存当前草稿 `draft`、收集状态及截止时间；`survey_versions` 保存已经发布的定义快照。题目、选项、校验和跳转规则嵌入定义，避免一次读取问卷需要拼接大量独立记录。

编辑已发布问卷时，题目、标题、描述和策略先写入草稿，再次发布后才成为新填写的定义。发布检查通过后，代码根据 `sourceDefinitionVersion` 判断是否需要新建快照；定义未改动的再次发布可以复用原快照。关闭后可以显式发布重新开放。

一次填写开始时，将 `publishedVersion` 和 `anonymous` 绑定到 `attempts`。后续读取、保存和提交均按该版本解释题目，因此旧填写不会因新发布而被套用新题目。截止时间和当前是否收集则始终读取当前问卷控制记录。

三个版本字段各司其职：`definitionVersion` 标识定义编辑，`controlRevision` 标识管理修改，`publishedVersion` 标识发布快照。当前代码仅修改截止时间时只增加控制修订号；发布、关闭也不增加定义编辑版本。

实现位置：[management.py](../../../code/survey_app/management.py) 的 `mutation`、`publish`、`close`；[filling.py](../../../code/survey_app/filling.py) 的 `start`、`version`。

## 2. 后端校验与确定性跳转

题目、选项、规则采用稳定 ID，排序使用题目 ID 列表，跳转引用 ID 而非可变题号。修改题序后仍须满足跳转目标位于当前题之后，或为 `END`；删除被引用的题目或选项会被拒绝。

`canonical_answers` 同时用于保存与最终提交，服务端按以下步骤构造可信答案：

1. 检查输入数组，拒绝未知题目、重复题目及不匹配的题型。
2. 从第一题开始遍历；按题型校验当前答案，不接受客户端指定填写路径。
3. 当前题缺少答案，或必答题为空时，停在该题并记录 `nextQuestionId`。保存允许这种未完成状态，提交不允许。
4. 对非空答案按 `priority` 升序匹配跳转，第一条命中即执行；无命中则进入下一题，`END` 则结束。
5. 只保留实际遍历并处理的答案，返回 `visitedQuestionIds`、下一待答题及被移除答案 ID。

保存是全量替换。修改前面答案导致路径变化时，原路径上的后续答案会被清除；路径外已知题目的值不进入答题统计。被合法跳过的必答题不要求回答。可选题若要跳过，也须显式发送对应空值，不能以字段缺失表示已经处理。

例如第一题选择“否”后直接跳到第三题，则第二题即使必答，也不阻止提交；若请求仍携带第二题的旧答案，服务端将其移除。

实现位置：[domain.py](../../../code/survey_app/domain.py) 的 `validate_definition`、`answer_value`、`matches`、`canonical_answers`。

## 3. 截止、关闭与提交并发

只在提交前读取一次问卷状态，可能出现“检查通过后管理员立即关闭，但提交仍写入”的竞争。当前实现使用问卷控制文档作为共同的事务写入点。

开始填写、保存和首次提交均调用 `gate`：要求 `state=PUBLISHED`，并用 MongoDB 的 `$$NOW` 检查截止时间为空或严格晚于当前时间；同时真正增加 `writeFence` 并更新 `lastGateAt`。发布、关闭和截止时间修改也写同一问卷文档，因此并发操作会产生写冲突并按事务机制重试，重新判断最新状态。

`acceptedAt` 取本次成功收集检查的数据库时间。截止判定依据这一检查时刻，不能理解为 HTTP 返回时刻或物理事务提交完成时刻。管理列表的 `effectiveState` 使用应用时钟辅助展示，实际收集准入仍以数据库检查为准。

已开始填写不能绕过后续截止或关闭检查；已经成功提交的原请求重试则优先读取提交凭据，即使此时已关闭，也可以返回原成功结果，不会接纳一份新答卷。

实现位置：[filling.py](../../../code/survey_app/filling.py) 的 `gate`、`save`、`submit`；[database.py](../../../code/survey_app/database.py) 的 `transaction`。

## 4. 原子提交、重复策略与提交顺序

`participation_guards` 对 `(surveyId, userId)` 建立唯一索引，每个账号在同一问卷下只有一个参与身份。开始填写和提交时，服务端读取**当前发布版本**的 `allowRepeat`，结合账号历史 `acceptedCount` 判断是否允许继续开始或提交。保存草稿不执行重复策略判断，但仍检查收集状态。

提交在同一个 MongoDB 多文档事务中执行：

1. 查找当前账号和幂等键对应的成功凭据；若为同一请求，直接返回原答卷信息。
2. 检查尝试所有权、未提交状态及 If-Match。
3. 执行收集检查和当前重复策略检查，按尝试绑定版本重新验证路径完整性。
4. 创建或更新参与守卫，增加 `acceptedCount`，把返回值作为 `submissionSequence`。
5. 向 `responses` 插入历史答卷，记录参与身份、接纳序号、绑定版本、规范化答案及实际访问路径。
6. 将尝试更新为 `SUBMITTED`，关联答卷并增加尝试修订号，同时写入 `submission_keys` 凭据。
7. 提交事务，统一使所有写入生效。

失败事务整体回滚，避免“人数已增加但答卷没有写入”等部分成功。`attemptId` 的答卷唯一索引防止一次尝试产生多份答卷，参与身份与序号的联合唯一索引防止序号重复。序号表示事务接纳顺序，不依据浏览器时间或客户端请求到达顺序。

事务采用 snapshot 读取和 majority 写入确认。暂态事务错误和唯一键竞争在预算内重新执行事务；若提交结果未知，则重试**同一次 commit**，不能直接重跑业务。仍无法确定时返回 503 `COMMIT_UNCERTAIN`，提示保留原请求重试。

实现位置：[filling.py](../../../code/survey_app/filling.py) 的 `repeat_check`、`submit`；[database.py](../../../code/survey_app/database.py) 的 `transaction`；[schemas.json](../../../code/数据库设计/schemas.json) 中的唯一索引。

## 5. 乐观锁与幂等分别解决不同问题

**乐观锁防止旧页面覆盖新数据。** 管理操作使用定义版本与控制修订号组成 ETag，填写使用尝试修订号组成 ETag。接口检查 `If-Match` 后，数据库更新条件仍携带原版本；并发修改只允许一个有效结果，陈旧请求返回 409，缺少条件头返回 428。

**幂等防止同一次提交因网络重试而重复入账。** 服务端对幂等键做 SHA-256 摘要，以账号和摘要建立唯一约束，并记录由账号、尝试 ID 和提交时 If-Match 计算的请求指纹。

相同键、相同指纹返回原 `responseId` 与 `submittedAt`，`replayed=true`；键相同但指纹不同返回 `IDEMPOTENCY_CONFLICT`。已提交尝试换新键重提返回 `ATTEMPT_SUBMITTED`。若允许再填，应新建尝试并使用新键，不应把成功提交过的尝试重新打开。

实现位置：[common.py](../../../code/survey_app/common.py) 的 ETag、摘要与指纹函数；[management.py](../../../code/survey_app/management.py) 的 `mutation`；[filling.py](../../../code/survey_app/filling.py) 的 `save`、`submit`。

## 6. 统计只使用每个账号的最新整份答卷

所有历史提交保留在 `responses` 中，但不直接按历史记录条数统计。统计首先按问卷匹配，再按 `participationId`、`submissionSequence` 倒序排列，按参与身份分组取第一份**完整答卷**，最后才进行版本、题目及非空答案筛选。

```text
问卷历史提交
  → 按参与身份、接纳序号排序
  → 每个参与身份取最新整份答卷
  → 按版本与题目筛选
  → 统计人数、选项、文本与平均值
```

例如同一账号在版本 1 选择 A，随后在版本 2 选择 B，则全问卷统计中该账号只贡献 B 的一人；筛选版本 1 时也不能重新计入其旧答卷。若最新答卷跳过某题，该题旧答案同样不能被补回。最新填写仍是草稿或提交失败时，上一份成功答卷继续有效。

单选题按选项计人数；多选题先保证选项不重复，每人每选项最多贡献一次。`reachedCount` 取实际路径人数，`answeredCount` 取非空作答人数，因此两者可能不同。

当前代码通过 MongoDB 聚合完成最新答卷去重，再流式读取受限字段，在应用内累加指标；没有直接照搬数据库设计示例中的 `$facet` 或 `$avg`。一次统计请求在同一快照事务内读取版本和答卷，跨分页请求则不承诺固定快照。

实现位置：[statistics.py](../../../code/survey_app/statistics.py) 的 `latest_prefix`、`metrics`、`answers`。

## 7. 数字精度与匿名输出

数字输入必须为十进制字符串，经 `Decimal` 校验后转换为 BSON Decimal128；无法精确表达、非有限值或不符合范围与整数限制的输入均被拒绝。数字边界和答案采用相同处理，避免 JSON 二进制浮点误差影响校验和统计。

平均值使用高精度 Decimal 累加与除法，按四位小数 `ROUND_HALF_UP` 舍入，去除尾零并以字符串返回；无有效数字时为 `null`。

匿名标志绑定在填写开始时的版本，提交匿名答卷时不写 `respondentUserId`。结果列表采用字段白名单，匿名条目只返回版本、答案、提交时间和匿名标志，省略用户名及内部关联标识。用于防重复和去重的 `participationId` 留在系统内部，分页内部定位信息封装进加密游标。因此这里提供的是对问卷创建者匿名，系统运营者仍可能通过内部数据关联账号。

实现位置：[domain.py](../../../code/survey_app/domain.py) 的 `decimal128`；[statistics.py](../../../code/survey_app/statistics.py) 的 `average`、`answers`；[filling.py](../../../code/survey_app/filling.py) 的答卷构造。

## 8. Schema、索引与会话保护

程序启动时读取 `数据库设计/schemas.json`，创建缺少的集合与索引，并核对现有校验器是否一致。八个集合使用 strict/error 校验；旧版答卷或不兼容结构会阻止启动，要求明确迁移或改用新库，不会自动覆盖旧结构。Schema 负责类型与结构，跨集合关系、跳转正确性和统计规则仍由业务代码保证。

业务约束通过用户名唯一、分享标识唯一、发布版本唯一、每账号问卷参与身份唯一和提交幂等唯一等索引落地；查询索引支持本人问卷列表、填写恢复及最新答卷查找。会话 TTL 索引用于清理过期记录，鉴权仍在每次请求检查 `expiresAt`，避免依赖 TTL 清理是否及时。

账号密码使用 Argon2 哈希，会话数据库中保存令牌摘要；修改操作检查 CSRF 与来源。请求速率限制为单进程内计数，适用于当前课程部署，不属于多实例共享限流。

实现位置：[database.py](../../../code/survey_app/database.py)、[security.py](../../../code/survey_app/security.py) 及[schemas.json](../../../code/数据库设计/schemas.json)。

本说明描述现有机制，不表示所有测试已经通过；已记录的手动失败和 API 失败保持原样。接口与设计约定的具体差异见 [API说明第 9 节](../../API说明/第一阶段/API说明.md#9-当前实现与设计文档的差异)。
